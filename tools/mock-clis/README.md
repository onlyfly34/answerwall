# Mock CLIs

One fake executable per CLI provider kind (`claude`, `codex`, `agy`, `grok`,
`opencode`).
Each accepts the argument shapes of the real CLI, replays a fixture in the
real CLI's output format, and can misbehave on request, so adapters and
end-to-end tests never need a real account or the network.

Nothing here talks to a vendor. The mocks never read a credential file.

## Layout

| Path                               | Content                                                                                 |
| ---------------------------------- | --------------------------------------------------------------------------------------- |
| `src/<kind>.mjs`                   | The mock: argument validation, status subcommands, the run mode.                        |
| `src/lib/runtime.mjs`              | Shared: strict flag parser, scenario selection, fixture replay, the scenarios.          |
| `fixtures/<kind>/*.jsonl`          | Output streams: scrubbed recordings, and `*.synthetic.jsonl` for what was not recorded. |
| `bin/<kind>`                       | POSIX launcher (a `sh` script).                                                         |
| `bin/<kind>.cmd`, `bin/<kind>.ps1` | Windows launchers in the exact form npm writes for a package's bin entry.               |

## Using the mocks

Put `bin/` first on the `PATH` handed to the provider registry (the `env`
dependency of `createProviderRegistry`), together with the directory of the
`node` executable:

```
PATH=<repo>/tools/mock-clis/bin:<dir of node>
```

On POSIX the adapters find `bin/claude` and run it. On Windows they find
`bin/claude.cmd`, which is never executed: executable resolution reduces the
shim to `node.exe <repo>\tools\mock-clis\src\claude.mjs` and starts that, the
same way it treats a CLI installed with `npm install -g`. There is no compiled
`.exe` form of the mocks; resolution of a native `.exe` on `PATH` is covered
by the resolver's unit tests against synthetic directory layouts.

The `bin` entries of `package.json` point at the same scripts, for a package
that wants them linked into its `node_modules/.bin`.

## Choosing a scenario

A model named `mock-<scenario>` selects the scenario for that run. Otherwise
the environment variable `MOCK_CLI_SCENARIO` does; the default is `ok`. The
status subcommands only look at the environment variable.

| Scenario             | Behaviour                                                                                          |
| -------------------- | -------------------------------------------------------------------------------------------------- |
| `ok`                 | A short answer, token by token where the CLI streams tokens, with usage.                           |
| `echo`               | Answers `You said: <prompt>`, to prove how the prompt travelled.                                   |
| `slow`               | The `ok` answer with `MOCK_CLI_DELAY_MS` (default 40) between lines.                               |
| `chunked`            | The `ok` answer with CRLF line endings, written seven bytes at a time.                             |
| `block`              | A whole message at once, no token deltas.                                                          |
| `reasoning`          | Reasoning before the answer.                                                                       |
| `tool-denied`        | The model asks for a tool; the call is denied; an answer follows.                                  |
| `incremental`        | codex only: one item growing through `item.updated` events.                                        |
| `hang`               | Prints nothing, does not read stdin, never exits.                                                  |
| `init-hang`          | Prints the first line of the `ok` answer, then never exits.                                        |
| `logged-out`         | The run fails as it does without a login; the status subcommand reports "not logged in".           |
| `quota`              | The run fails with the usage limit reached.                                                        |
| `rate-limited`       | The run fails after being rate limited. `opencode`: see below.                                     |
| `model-not-found`    | The run fails because the model does not exist.                                                    |
| `exit-nonzero`       | Exit code 3 with a diagnostic on stderr that contains a path.                                      |
| `garbage`            | Plain text instead of the documented format, exit code 0.                                          |
| `huge`               | An answer of `MOCK_CLI_HUGE_BYTES` (default 3 MiB).                                                |
| `stderr-noise`       | The `ok` answer with tens of kilobytes of noise on stderr between the lines.                       |
| `tree`               | Starts a child that ignores SIGTERM and shares stdout, prints one line, then never exits.          |
| `stubborn-tree`      | Like `tree`, but the CLI itself ignores SIGTERM too, so only SIGKILL ends it.                      |
| `lingering-child`    | Answers and exits, while a child it started keeps stdout open.                                     |
| `own-session-child`  | Like `tree`, but the child is in a session of its own and exits when the pipe from the CLI closes. |
| `own-session-orphan` | Like `own-session-child`, but the child ignores the end of that pipe (it exits after a minute).    |

The mocks that take their prompt on stdin (`claude`, `codex`, `agy`,
`opencode`) answer
only after stdin has been closed, so an adapter that forgets to close it
hangs here exactly as it would with the real CLI. `grok` never reads stdin.

Set `MOCK_CLI_LOG` to a file and every invocation appends one JSON line to
it: `kind`, `pid`, `argv`, `cwd`, the names of all environment variables, the
values of a few fixed ones, the scenario and the prompt it received. The
`tree`, `stubborn-tree` and `lingering-child` scenarios also log `grandchildPid`. That child's
command line ends with the mock's script path and `stubborn-child`, so
`pgrep -af 'src/(claude|codex|grok|agy|opencode).mjs'` lists it with the mocks when
something has left it behind.

The `own-session-*` scenarios log `detachedPid` instead. That child is what
the private server of `opencode run --standalone` is to the real CLI: it
leads a session and process group of its own, so a signal to the process
group of the CLI does not reach it, and its stdin is a pipe from the CLI.
`own-session-child` ends when that pipe closes, as the real server did.
`own-session-orphan` does not, and nothing in the application removes it: the
test that uses it asserts that it is still there and kills it itself. Its
command line ends with the mock's script path and `own-session-child`.

Every line also carries `at`, the time it was written. A suite that looks for
leftover mocks needs it: Windows hands the process id of an ended process to
one of the next that start, so a recorded id that is "alive" may be another
program by then. `src/lib/leftovers.mjs` reads the log and returns only the
recorded processes that are really still running (on Windows, those whose
process was created before the line was written). The e2e suite and
`pnpm smoke:mock` use it, and only what it returns is ever killed.

Set `MOCK_CLI_REMOVED_FEATURE` to a feature name and the mock `codex` treats
that name as one it does not know: it prints `Error: Unknown feature flag:
<name>` and exits 1, as the real CLI does for any unknown `--disable` name.

The mock `codex` also insists on the configuration overrides of the confirmed
invocation: each `-c` setting listed under "codex" below exactly once, one of
`web_search="disabled"` and `web_search="live"`, at most one
`model_reasoning_effort="<level>"`, and no other override.

The mock `claude` accepts `--tools` in two forms only: `""` alone, or
`WebSearch` together with `--allowedTools WebSearch`. Anything else, such as
a second tool or a missing allow rule, is a usage error.

## Strictness

An argument the mock does not know, a missing required argument, a wrong
value, a prompt in the wrong place or a missing environment setting ends the
mock with exit code 64 and a message on stderr. This is deliberate: when an
adapter's invocation drifts from what is written down here, its tests fail.
The same happens when a variable named `ANSWERWALL_*` (the application's own
settings and secrets) is in the mock's environment, whatever the command: a
CLI child must never receive those.
When phase P1 changes an invocation, change the adapter's `build…Args`
function, its unit test, and the flag table of the mock together.

## Fixtures

A fixture is one JSON event per line after a `#` header line. There are two
kinds, told apart by the file name:

- `<scenario>.jsonl` is a recording of a real run. Its header starts with
  `# recorded from <cli> <version>, scrubbed` and says how the run was made.
  Session, message and request ids, paths, timestamps, signatures and account
  details were replaced by fixed placeholders before the file was saved.
- `<scenario>.synthetic.jsonl` was written by hand, for a shape that could not
  be recorded (a failure that cannot be provoked safely, a mode the adapter
  does not use). Its header starts with `# synthetic` and says what it is
  based on.

A scenario uses the recording when there is one, otherwise the synthetic
file. A fixture that belongs to no scenario is read by the adapter's unit
tests; the mock `claude` and the mock `codex` also play their
`web-search.jsonl` as the `ok` answer when they are started with the web
search switched on (`--tools WebSearch --allowedTools WebSearch`, or
`-c web_search="live"`), which is how an instance with "allow web search" on
is tested end to end. One line is not replayed as
recorded: the `tools` list in the init line of the claude `tool-denied` run
(recorded with the search tool offered, without its allow rule) is replaced by
what the mock was started with.

## What is confirmed and what is assumed

`pnpm smoke:real` re-checks the confirmed parts on demand: it sends one tiny
prompt through each installed, logged-in real CLI with the adapter's own
arguments and reports what the CLI said about its session. It is a manual
command that uses the owner's account; nothing in this directory, in CI or in
any other script starts it.

"Confirmed" means checked on a machine with the CLI installed (claude
2.1.330, codex-cli 0.167.0): by reading `--help` output, by running a status
subcommand, or, where the source column says "real run", by sending a tiny
prompt and reading what came back. `agy` and `grok` were not installed;
everything about them comes from their documentation. `opencode` was
confirmed against a local stub endpoint instead of a vendor; see its section.

The mock `opencode` reads `opencode.json` from its working directory, as the
real CLI does, and insists on what the adapter is expected to write: a
primary agent named `answerwall` with a system prompt and the single rule
that denies everything, the four policies, and no provider, model, MCP or
plugin setting. Without the file, or with `OPENCODE_DISABLE_PROJECT_CONFIG=1`
on a run, it answers `Agent not found` like the real CLI. A model is
`provider/model`; the scenario is named by the model part
(`mock/mock-echo`). Its `auth list` and `models` commands are a usage error
without `--standalone` or unless both `OPENCODE_DISABLE_PROJECT_CONFIG` and
`OPENCODE_CONFIG_PROJECT_DISABLE` are `1`; on a run it decides as the real
binary does (the second name wins whenever it is set). Set
`MOCK_OPENCODE_LEGACY=1` and it behaves like version 1.

Its `rate-limited` scenario prints the recording up to the first `retry`
line, waits `MOCK_OPENCODE_RETRY_MS` (default 1500), appends a log line with
`resent: true`, and only then prints the remaining `retry` lines and the
`error` line. The adapter ends the run at the first `retry` line, so its
tests assert that no `resent` line is ever written.
